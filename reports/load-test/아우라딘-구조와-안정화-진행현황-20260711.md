# 아우라딘 구조와 안정화 진행 현황 - 2026-07-11

## 이 문서의 목적

이 문서는 아우라딘을 직접 구현하지 않은 팀원도 다음 내용을 이해할 수 있도록 정리한 문서다.

- 아우라딘이 사용자에게 제공하는 기능
- 한 번의 추천 요청이 서버에서 처리되는 과정
- 지금까지 발견하고 수정한 문제
- 초기 등록 사용자 200명을 기준으로 확인한 성능
- 앞으로 검증해야 할 항목과 판단 기준

## 아우라딘이 하는 일

아우라딘은 사용자가 원하는 화장품 조건을 자연어로 입력하면 조건을 해석하고, 필요한 경우 추가 질문을 한 뒤 적합한 상품을 추천하는 대화형 상품 추천 기능이다.

사용자 입력 예시:

> 쿨톤인데 너무 진하지 않은 글로시 핑크 립을 2만원 이하로 추천해줘

아우라딘은 이 문장에서 다음과 같은 조건을 추출한다.

- 상품 종류: 립
- 색상과 분위기: 핑크, 너무 진하지 않음
- 제형: 글로시
- 가격: 2만원 이하
- 사용자 특성: 쿨톤

조건이 부족하면 색상, 제형, 가격대 같은 추가 질문을 보여준다. 조건이 충분해지면 후보 상품의 점수를 계산하고 최종 추천 상품을 반환한다.

## 얼굴진단과 다른 점

얼굴진단, 메이크업 피드백, 레퍼런스 추출은 시간이 오래 걸리는 AI 분석 작업이다. 이 기능들은 현재 SQS와 ECS 워커로 분리되어 있다.

아우라딘은 현재 다르다.

- FastAPI가 사용자 요청을 직접 받는다.
- FastAPI 안에서 후보 검색과 순위 계산을 수행한다.
- 필요한 경우 Naver 쇼핑 API와 Bedrock 응답을 기다린다.
- 처리가 끝난 뒤 세션 생성 또는 답변 요청에 응답한다.

따라서 아우라딘 사용자가 많아지면 얼굴진단 워커가 아니라 FastAPI API 서버에 직접 영향을 줄 수 있다.

## 현재 요청 처리 흐름

```text
모바일 앱
  -> API Gateway에서 JWT 인증
  -> FastAPI 아우라딘 API
  -> 사용자 문장 해석
  -> 내부 상품 목록 검색 및 순위 계산
  -> 조건이 부족하면 Bedrock으로 질문 문구 보강
  -> 결과 단계면 Naver에서 최신 판매 상품 검색
  -> Bedrock으로 추천 이유 문구 보강
  -> 세션 상태를 Postgres에 저장
  -> 모바일 앱이 세션을 조회하여 질문 또는 결과 표시
```

주요 API:

| 기능 | API |
|---|---|
| 추천 세션 시작 | `POST /api/search/sessions` |
| 현재 질문 또는 결과 조회 | `GET /api/search/sessions/{sessionId}` |
| 질문 답변 | `POST /api/search/sessions/{sessionId}/answer` |
| 추천 조건 다시 조정 | `POST /api/search/sessions/{sessionId}/refine` |
| 추천 중단 | `POST /api/search/sessions/{sessionId}/cancel` |

## Naver와 Bedrock의 역할

### Naver 쇼핑 API

내부 상품 목록만으로 발견용 추천 상품이 부족할 때 현재 판매 중인 상품을 검색한다. 가격과 구매 링크를 보강하는 역할도 한다.

### Bedrock

상품을 직접 검색하거나 순위를 결정하는 핵심 엔진은 아니다. 현재는 다음 문구를 자연스럽게 만드는 보조 역할을 한다.

- 사용자에게 보여줄 추가 질문 문구
- 추천 상품별 추천 이유 문구

Bedrock 호출에 실패하거나 제한시간을 넘겨도 규칙 기반 기본 문구로 결과를 반환하도록 구성되어 있다.

## 기존에 있었던 문제

### 1. 아우라딘 세션을 API 메모리에만 저장

세션에는 사용자의 최초 입력, 지금까지 선택한 답변, 적용된 조건, 후보 상품, 현재 질문이 들어 있다.

기존에는 이 상태를 FastAPI 프로세스의 메모리에 저장했다. 이 방식은 다음 문제가 있다.

- API 서버를 재시작하면 진행 중인 추천이 사라진다.
- API 태스크를 2개로 늘리면 다른 태스크가 세션을 찾지 못할 수 있다.
- Auto Scaling을 켜도 세션이 공유되지 않아 안정적인 확장이 어렵다.

### 2. Postgres 모드에서도 오래된 메모리가 DB를 덮어쓸 위험

Postgres 저장 코드가 이미 일부 있었지만 메모리에 세션이 있으면 DB의 최신 상태보다 메모리를 우선했다. 여러 API 태스크가 같은 세션을 처리하면 이전 답변 상태가 최신 상태를 덮어쓸 수 있었다.

### 3. 최초 로그인 사용자의 동시 요청 충돌

로그인 직후 앱에서 여러 API가 동시에 호출되면 같은 사용자를 RDS에 여러 번 생성하려고 시도했다. 실제 부하 테스트에서 1,000건 중 16건이 500 오류로 실패했다.

오류 원인:

```text
duplicate key value violates unique constraint idx_users_provider_sub
```

## 지금까지 수정한 내용

### 아우라딘 세션을 Postgres로 전환

- 운영 기본 저장소를 Postgres로 변경했다.
- 세션 조회 시 DB의 최신 상태를 우선한다.
- DB에 세션이 없으면 오래된 메모리 세션을 반환하지 않는다.
- 단순 상태 조회 때마다 같은 세션을 다시 저장하던 불필요한 DB 쓰기를 제거했다.
- AWS API 태스크 정의 50번에 배포했다.

기능적으로는 사용자가 질문에 답하는 도중 API 서버가 바뀌어도 추천 대화가 이어질 수 있게 만든 것이다.

### 사용자 생성을 원자적 처리로 변경

기존의 조회 후 생성 방식을 PostgreSQL의 단일 upsert로 변경했다.

```text
INSERT ... ON CONFLICT ... DO UPDATE
```

같은 사용자의 첫 요청이 동시에 들어와도 한 행만 생성되고 나머지 요청은 같은 행을 사용한다.

## 비용 없는 부하 테스트 결과

외부 AI 비용이 생기지 않도록 지원하지 않는 상품 종류인 향수 요청을 사용했다. 이 요청도 세션 생성, Postgres 저장, 상태 조회, 취소 경로는 실제 아우라딘과 동일하게 거친다.

### 일반 API 기준값

| 항목 | 결과 |
|---|---:|
| 동시 요청 | 20개 |
| 총 요청 | 1,000개 |
| 성공 | 1,000개 |
| 실패 | 0개 |
| 응답시간 p95 | 112ms |

### 아우라딘 세션 20개와 일반 API 동시 실행

| 항목 | 결과 |
|---|---:|
| 아우라딘 세션 | 20개 모두 성공 |
| 일반 API | 1,000개 모두 성공 |
| 아우라딘 세션 생성 p95 | 292ms |
| 아우라딘 상태 조회 p95 | 159ms |
| 일반 API 응답시간 p95 | 158ms |
| API ECS CPU 최대 사용률 | 39.9% |
| RDS CPU 최대 사용률 | 5.7% |
| RDS 연결 수 | 5개 |

결론:

- Postgres 세션 저장 자체는 초기 등록 사용자 200명 기준 병목이 아니다.
- 아우라딘 세션 요청이 20개 겹쳐도 일반 API 실패는 없었다.
- 일반 API p95가 112ms에서 158ms로 늘었지만 아직 충분히 빠른 범위다.

## 부하 테스트 중 추가로 수정한 문제

새 임시 사용자의 첫 API 요청 20개를 동시에 보내 사용자 생성 경쟁 조건을 재현했다.

| 상태 | 성공 | 실패 |
|---|---:|---:|
| 수정 전 | 984개 | 16개 |
| 원자적 upsert 수정 후 첫 동시 요청 | 20개 | 0개 |
| 수정 후 일반 API 재측정 | 1,000개 | 0개 |

## 아직 확인하지 않은 부분

비용 없는 테스트에서는 실제 Naver와 Bedrock을 호출하지 않았다. 따라서 다음 항목은 아직 결론을 내릴 수 없다.

- Naver와 Bedrock 호출이 동시에 5개 발생할 때 일반 API가 얼마나 느려지는지
- Bedrock 제한시간 또는 호출 제한이 발생하는지
- 실제 아우라딘 전체 추천 여정이 몇 초 걸리는지
- 아우라딘을 FastAPI에 유지해도 되는지, 별도 SQS와 워커로 분리해야 하는지

## 다음 실측 순서

### 1단계: 실제 전체 여정 1개

- 대표 립 추천 문장으로 세션 시작
- 추가 질문에 자동으로 답변
- 최종 추천 결과까지 진행
- 동시에 일반 API 요청을 보내 영향 측정
- Bedrock, Naver, 세션 오류 확인

### 2단계: 실제 전체 여정 5개 동시 실행

- 초기 등록 사용자 200명 중 2.5%가 동시에 아우라딘을 실행하는 상황
- 일반 API 1,000건을 함께 실행
- 일반 API 응답시간, API CPU, RDS CPU, 5xx 확인

### 3단계: 구조 결정

다음 조건을 모두 만족하면 초기 200명 단계에서는 아우라딘을 FastAPI에 유지할 수 있다.

- 일반 API 5xx가 0건
- 일반 API p95가 500ms 이하
- API ECS CPU가 70% 이하
- RDS 연결 수와 CPU가 안정적
- 아우라딘 요청이 서버 제한시간 안에 완료

조건을 만족하지 못하면 다음 구조로 분리한다.

```text
FastAPI
  -> 아우라딘 세션 생성 및 빠른 응답
  -> 전용 SQS에 작업 발행
  -> 아우라딘 전용 ECS 워커가 Naver와 Bedrock 처리
  -> Postgres 세션 결과 갱신
  -> 앱이 상태 조회
```

얼굴진단 작업과 같은 큐를 공유하면 긴 이미지 작업에 아우라딘이 밀릴 수 있으므로, 분리할 경우 아우라딘 전용 큐와 워커를 사용한다.

## 실제 호출 수 안내

현재 구현에서 전체 아우라딘 여정 1개는 질문 문구와 추천 이유 문구 생성을 위해 Bedrock을 보통 약 6회 호출한다. 결과 검증 재시도가 발생하면 최대 약 9회까지 늘어날 수 있다.

- 1명 검증: 약 6~9회 Bedrock 호출
- 동시 5명 검증: 약 30~45회 Bedrock 호출

따라서 실제 여정 테스트는 소액이지만 비용이 발생하며, 사용자 확인 후 실행한다.
